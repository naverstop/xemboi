## 1. 목적
시장 내에서 **항상 경쟁사보다 가격 우위**를 유지하기 위해, 경쟁사 가격을 주기적으로 반영해
우리 메뉴별 권장가를 산출하고, 관리자 승인(또는 완전자동)으로 라이브에 즉시 반영하는 루프를 만든다.

**2단 자동화(운영자 요구 #7·#8)**
- **1단계(안정화)**: 주단위 조사 토글 ON → 권장가 산출 → 관리자 탭에 표시 → 관리자가 **[적용] 클릭** → 라이브 반영.
- **2단계(완전자동)**: 최상단 **AI 가격 적용 토글** ON → 조사→가드레일 통과분 **자동 적용**→알림. OFF면 1단계처럼 클릭 대기.

## 3. 데이터 소스 — 관리자 수동 경쟁사 시트 (확정)
자동 크롤은 불가/취약(앱 인앱가는 앱스토어·로그인 뒤, 웹가는 구조변경 취약, deep-research는 Claude Code 전용).
→ **관리자가 경쟁사 가격을 시트로 관리**하고, 배치는 그 시트를 근거로 권장가를 계산한다.

**이점**: 권장가 산출이 **결정적 계산**(LLM·GPU·크롤 없음)이 되어 100% 재현·감사·테스트 가능.
(선택) 후속 차수에 LLM을 **근거 문장 생성·이상치 경고**에만 얹을 수 있음 — 핵심 계산은 항상 결정적 유지.

**운영 흐름**: 관리자가 주1회 경쟁사 가격 확인→시트 갱신(`verified_at` 갱신) → 주단위 잡이 권장가 재산출.
시트가 오래되면(예: 14일 초과) 관리자 탭에 "데이터 낡음" 경고 배지.

## 4. 데이터 모델 (신규 테이블 3개)
```
competitor_prices           -- 관리자 수동 관리(경쟁사 시트)
  id, competitor_name, menu_key(우리 키), price_krw, note,
  verified_at, updated_by, created_at

pricing_guardrails          -- 메뉴별 가격 가드레일(관리자 설정)
  menu_key PK, floor_p, ceiling_p, max_change_pct, undercut_pct,
  round_unit(예: 100), round_tail(예: 900=…,900원 앵커), enabled

pricing_recommendations     -- 주단위/수동 산출 결과(승인 대기·이력)
  id, batch_id, menu_key, current_price, competitor_min, competitor_median,
  recommended_price, rationale, status(pending|applied|dismissed|skipped),
  created_at, decided_at, decided_by
```
모두 BigInteger PK는 `with_variant(Integer, "sqlite")` 적용(테스트 호환, 기존 규칙).

**신규 설정키 2개**(둘 다 초기 `"false"`): `pricing_survey_enabled`(주단위 조사 ON/OFF),
`pricing_auto_apply_enabled`(완전자동 마스터). → `DEFAULTS`+`_BOOL_KEYS`+`admin.py SettingsPatchReq`+`api.ts` 4곳 등록.

## 4-B. 가드레일 기본안 (운영자 확정 2026-07-13 — 시드값)
| 메뉴 그룹 | 키 | 언더컷% | 최대변동% | 하한 | 상한 | 반올림(unit/tail) |
|---|---|---|---|---|---|---|
| 입장(커머디티) | tarot·compat·aho | 5 | 25 | 3,900 | 19,900 | 1000 / 900 |
| 입장(전문) | jakmyeong·gaemyeong·taekil·sinnyeon | 5 | 25 | 4,900 | 29,900 | 1000 / 900 |
| 질문 | credit_cost_basic·credit_cost_deep | 10 | 25 | 900 | 9,900 | 1000 / 900 |
| 부가 | amulet_cost_p·video_gen_cost·preview_reveal_cost | 5 | 30 | 900 | 9,900 | 1000 / 900 |
| 상담 | consultation_default_price_p | 3 | 20 | 30,000 | 120,000 | 1000 / 0 |
- 반올림: `tail=900` → 끝자리 900(…,900원 앵커, unit=블록 1000), `tail=0` → unit 배수. **유효 구간(하한/상한 ∩ 최대변동 밴드 ∩ 언더컷 상한) 안의 최근접 앵커**를 선택(반올림이 경계를 넘지 않음).
- max_change=25~30%: …900 앵커 간격(1000)을 한 스텝 넘도록(작은 가격도 이동 가능). max_change=0 = 동결(무제한 아님).

## 5. 권장가 산출 알고리즘 (결정적)
각 `menu_key`(경쟁사 데이터 존재 시):
1. `competitor_min = min(해당 키에 매핑된 경쟁사가)`, `competitor_median = median(...)`
2. `target = competitor_min × (1 − undercut_pct/100)`  … **항상 언더컷(#5)**
3. `target = clamp(target, floor_p, ceiling_p)`  … 하한/상한 가드
4. **1회 최대변동 제한**: `|target − current| > current × max_change_pct/100` 이면 그 방향으로 상한만큼만 이동(급변 방지)
5. **심리가 반올림**: `round_unit`·`round_tail` 적용(예: 5,900 / 9,900 / 12,900 앵커)
6. `recommended_price` 확정. `rationale` = "경쟁사 최저 N · X% 우위 · 가드레일(하한/상한/최대변동) · 반올림"
- 경쟁사 데이터 없는 키 → `status=skipped`(권장 안 함, 현재가 유지).
- `recommended == current` → `status=skipped`(변경 없음).

## 6. 승인 게이트 상태머신 (자동적용 금지 — 운영자 최종 확정)
```
주1회 스케줄 틱 & pricing_survey_enabled=ON  (또는 관리자 "지금 조사")
  → 권장가 산출(§5) → pricing_recommendations 에 batch 적재(status=pending) → 관리자 알림
  → ⛔ 스케줄러는 여기까지. 절대 자동 적용하지 않는다.
관리자 [적용] 클릭(pending) → set_many + status=applied + decided_by/at 기록  ← 유일한 가격변경 경로
관리자 [무시] 클릭         → status=dismissed
```
- `pricing_auto_apply_enabled` 설정키는 정의만 하고 **본 차수엔 어떤 코드도 이 값을 읽어 자동적용하지 않음**
  (미래 확장 자리표시자). 스케줄러/API 어디에도 승인 우회 경로 없음.
- 초기 안정화: 조사 토글 ON → 관리자가 권장 확인·**수동 적용** 반복.

## 7. 스케줄러 통합 (주단위)
`scheduler.py`에 잡 추가(기존 패턴 그대로):
```python
# 주1회(예: 월요일 05:00) 가격 조사·권장 산출. pricing_survey_enabled 게이트 + 주차 중복방지.
if s.pricing_survey_enabled and now.weekday()==0 and now.hour==5 and now.minute==0
   and _last_pricing_week != iso_week(now):
    _last_pricing_week = iso_week(now)
    _run_pricing_survey()   # 인프로세스 or 경량 배치(결정적 계산이라 GPU/LLM 불필요)
```
- 산출은 순수 DB 계산 → 인프로세스 실행 가능(캐시 즉시 반영). 서브프로세스 불필요.
- 수동 트리거 `run_pricing_survey_now()`(관리자 "지금 조사" 버튼) — `run_nightly_learning_now` 패턴.

## 8. 적용 배관 (⚠️ 3소스 동기화 — 이번 세션 핵심 교훈)
가격 적용 시 **반드시**:
1. DB `app_settings` ← `set_many`(20초 TTL로 라이브)
2. `settings_service.DEFAULTS` ← 코드 상수(신규설치/키누락 대비, 핸드오버)
3. `frontend/src/lib/entryFee.ts` ENTRY_FALLBACK ← 비로그인 표시 폴백

→ 자동 적용(auto_apply)은 런타임에 (1)만 즉시 반영 가능. (2)(3)은 **코드 상수**라 배포 필요.
  **해결책**: auto_apply는 (1) DB만 갱신하되, 관리자 탭에 "코드 폴백 동기화 필요(N건)" 배지 + 스크립트 제공.
  또는 DEFAULTS/FALLBACK을 "DB 우선, 없으면 코드" 구조라 실사용엔 DB가 이기므로 **기능상 정확**하고,
  (2)(3)은 다음 배포 때 일괄 맞추면 됨(로그인 사용자·실차감은 항상 DB=정확, 비로그인 표시만 폴백).
  → **1단계는 관리자에게 3소스 diff를 보여주고, 배포용 patch를 자동 생성**하는 선에서 안전 확보.
